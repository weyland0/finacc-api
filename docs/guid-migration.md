# Переход на UUID

Все первичные ключи и ссылки между сущностями используют `Guid` / `Guid?` в C# и `uuid` в PostgreSQL. Это относится также к составному ключу `role_permissions`, членству в организации, родительским категориям и полям аудита `CreatedBy` / `UpdatedBy`.

`Entity.Id` получает `Guid.CreateVersion7()` при создании объекта. ID доступен до добавления в `DbContext` и сохраняется без изменений. Конфигурации EF используют `ValueGeneratedNever()`: автоинкремента и генерации UUID на стороне БД нет. PostgreSQL 18 и расширения для UUID v7 не требуются.

При прямых SQL-вставках необходимо явно передавать UUID. Системные записи в миграции и скрипте разрешений имеют фиксированные UUID v7; новые прикладные записи получают новые значения автоматически в приложении.

## Изменения API

- Идентификаторы в JSON передаются строками UUID, например `"id": "019a6139-6000-7000-8000-000000000001"`.
- Параметры маршрутов Categories и Counterparties используют ограничение `:guid`; числовые маршруты больше не подходят.
- Проверки положительных числовых ID заменены проверками на `Guid.Empty`.
- `null` у `Category.OrganizationId` по-прежнему означает глобальную категорию, а у `ParentCategoryId` — отсутствие родителя.
- JWT содержат UUID пользователя. Старые JWT с числовыми ID отклоняются; клиент должен очистить сохранённую сессию и войти заново.

## Пересоздание тестовой базы

Старые миграции с числовыми ключами заменены одной начальной миграцией `20261108114139_InitialCreate`. Она предназначена для пустой базы. Перенос существующих данных и обновление старой базы поверх прежней истории миграций не предусмотрены.

Команды выполняются из корня репозитория. Строка подключения `ConnectionStrings:DefaultConnection` берётся из существующей конфигурации приложения, включая user-secrets в Development. Сначала проверьте целевую базу:

```sh
dotnet ef dbcontext info --project src/FinaccApi
```

Следующая команда удаляет выбранную базу и все её данные. Она предназначена для согласованного пересоздания тестовой базы:

```sh
dotnet ef database drop --project src/FinaccApi --force
dotnet ef database update --project src/FinaccApi
```

Начальная миграция создаёт роль `owner` и выдаёт ей девять разрешений реализованных модулей:

- `Organization.View`, `Organization.Update`;
- `Categories.View`, `Categories.Create`, `Categories.Update`;
- `Counterparties.View`, `Counterparties.Create`, `Counterparties.Update`, `Counterparties.Archive`.

Пользовательские записи и организации не создаются. После пересоздания можно зарегистрировать пользователя и создать организацию через onboarding: роль владельца уже доступна. Дополнительные роли и их права настраиваются отдельно.

[Скрипт разрешений контрагентов](sql/register-counterparty-permissions.sql) остаётся повторно применимым и может использоваться после добавления дополнительных системных ролей.

## Проверка

```sh
dotnet build FinaccApi.sln --no-restore -m:1 -nodeReuse:false -p:UseSharedCompilation=false
dotnet test FinaccApi.sln --no-restore -m:1 -nodeReuse:false -p:UseSharedCompilation=false
dotnet ef migrations has-pending-model-changes --project src/FinaccApi --no-build
dotnet ef migrations script --project src/FinaccApi --no-build
```

Тесты проверяют UUID v7 до сохранения, сохранение идентификаторов и связей, UUID-типы ключей модели PostgreSQL, дерево категорий, изоляцию организаций, аудит и обработку пустых/числовых ID в JWT.

Проверено 8 ноября 2026 года:

- Сборка без ошибок и предупреждений; 105 из 106 тестов успешны.
- EF Core подтвердил отсутствие расхождений модели и snapshot.
- На отдельной временной базе PostgreSQL 16.8 выполнены миграции `Up → Down → Up`; проверены 23 UUID-колонки ключей и аудита.
- SQL-скрипт разрешений дважды выполнен без дубликатов и ошибок.
- Пройдены 29 HTTP-проверок: регистрация, вход, JWT с UUID и отклонение числовых/пустых ID, onboarding, дерево категорий, чтение и изменение записей, архивирование контрагентов. Проверочная база удалена после завершения.

Известный отдельный дефект: `RegisterHandlerTests.Handle_WhenEmailAlreadyExists_ReturnsFailure` падал до перехода и продолжает падать: `RegisterHandler` вычисляет `emailExists`, но не обрабатывает его. Поведение регистрации дубликатов не изменялось в рамках перехода.
